
# MyNaksh — Personalized AI Chat

A personalized AI chat backend built using Python, FastAPI, SQLite, and Azure OpenAI.

The application maintains short-term conversation history and persistent long-term user memories to generate personalized responses across multiple chat sessions.

## 1. Features

- REST API for personalized AI conversations.
- Short-term conversation history within each session.
- Persistent long-term memory across sessions.
- Selective extraction of user goals, interests, and preferences.
- Relevance-based memory retrieval using category filtering and keyword matching.
- Support for updating preferences and preserving multiple distinct goals.
- User-specific conversation and memory isolation.
- Azure OpenAI integration.
- Automated testing using Pytest.

## 4. Setup Instructions

### Prerequisites

- Python 3.12
- pip
- Azure OpenAI API credentials
- Azure OpenAI chat model deployment

### Step 1: Clone the Repository

```bash
git clone <repository-url>
cd mynaksh-ai-chat
```

Replace `<repository-url>` with the GitHub repository URL.

### Step 2: Create a Virtual Environment

Windows PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
```

### Step 3: Install Dependencies

```powershell
python -m pip install -r requirements.txt
```

### Step 4: Configure Azure OpenAI

Create a `.env` file in the project root using `.env.example`.

```env
AZURE_OPENAI_API_KEY=your_api_key
AZURE_OPENAI_ENDPOINT=https://your-resource.openai.azure.com/
AZURE_OPENAI_API_VERSION=your_supported_api_version
AZURE_OPENAI_DEPLOYMENT=your_chat_model_deployment
```

Replace the placeholder values with your Azure OpenAI configuration.

Never commit actual API keys or the `.env` file to GitHub.

### Step 5: Run the Application

```powershell
python -m uvicorn app.main:app --reload
```

The application initializes the SQLite database automatically during startup.

API URL:

http://127.0.0.1:8000

Swagger UI:

http://127.0.0.1:8000/docs

## 5. API Endpoints

### GET /health

Checks whether the application is running.

Response:

```json
{
  "status": "ok"
}
```

### POST /chat

Accepts a user message and returns a personalized AI response.

Request:

```json
{
  "user_id": "user-123",
  "session_id": "session-1",
  "message": "I'm planning to switch jobs next year, and I prefer advice in Hindi."
}
```

Example response:

```json
{
  "user_id": "user-123",
  "session_id": "session-1",
  "response": "अगले साल नौकरी बदलने के लिए अपनी स्किल्स और इंटरव्यू तैयारी पर ध्यान दें।",
  "context_used": [
    "language_preference",
    "career_goal"
  ]
}
```

The response text is generated by Azure OpenAI and may vary.

`context_used` contains the categories of memories selected for the current request.

The request fields `user_id`, `session_id`, and `message` are required and must contain at least one character.

### Component Responsibilities

**app/main.py**

Handles API requests and coordinates conversation history, memory extraction, retrieval, and response generation.

**app/llm.py**

## 7. Short-Term Conversation Memory

Short-term memory stores recent user and assistant messages within a specific session.

Conversation messages are associated with:

- user_id
- session_id
- role
- content
- created_at

The application retrieves recent messages using both `user_id` and `session_id`.

The database retrieval function uses a default limit of 10 messages.

### Example

First message:

```text
I have a Microsoft interview on Monday.
```

Follow-up in the same session:

```text
Which company did I mention?
```

The assistant can answer:

```text
You mentioned Microsoft.
```

This works because the previous conversation messages are included in the LLM context.

## 8. Long-Term User Memory

Long-term memory stores selected user information across different sessions.

Unlike conversation history, these memories are associated with the user rather than an individual session.

### Supported Memory Types

| Memory Type | Example |
|-------------|---------|
| career_goal | I'm planning to switch jobs next year |
| learning_goal | I want to learn Python |
| language_preference | Hindi |
| response_preference | Short answers |
| interest | I'm interested in astrology |
| location | Bangalore |

### Memory Extraction

The application uses regular expressions to identify supported user information.

Example:

```text
I want to learn Python.
```

Extracted memory:

```json
{
  "learning_goal": "I want to learn Python"
}
```

Not every message is saved as long-term memory.

For example:

```text
What is the weather today?
```

does not match the supported memory extraction patterns.

### Memory Updates

The database preserves multiple distinct goals within the same category.

For example:

```text
I want to learn Python.
I want to learn Docker.
```

Both learning goals can be stored.

Single-value preferences, such as language preference, are updated when a new supported preference is provided.

For example, changing a preference from Hindi to English replaces the previous language preference.

## 9. Relevant Memory Retrieval

The application uses category filtering and keyword-overlap scoring to select relevant memories.

Retrieval steps:

1. Identify keywords in the current user message.
2. Match query keywords with supported memory categories.
3. Compare specific query words with stored memory values.
4. Prefer memories with the highest keyword-overlap score.
5. Include applicable global preferences, such as language preference.

### Example

Stored memories:

```text
learning_goal: I want to learn Python
learning_goal: I want to learn Docker
learning_goal: I want to learn Kubernetes
```

User query:

```text
How should I start learning Python?
```

Selected memory:

```text
learning_goal: I want to learn Python
```

For a generic query such as:

```text
What skills should I learn?
```

Multiple learning goals may be retrieved.

This approach was chosen because the assignment permits lightweight rule-based retrieval without requiring embeddings or a vector database.

## 10. LLM Integration

The application uses the Azure OpenAI Python SDK.

The LLM receives:

- A system message containing assistant instructions and relevant user memories.
- Recent conversation history.
- The current user message.

The system prompt instructs the assistant to use relevant memories, avoid inventing personal information, and treat stored memories as contextual data rather than instructions.

The Azure OpenAI client uses:

- A 30-second request timeout.
- One configured retry.

If the LLM provider raises an exception, the API logs the failure and returns HTTP 502.

The LLM integration is separated into `app/llm.py` so it can be mocked during automated testing.

## 11. Database Design

SQLite stores conversation history and long-term memories.

### Conversations Table

```text
conversations
-------------
id
user_id
session_id
role
content
created_at
```

### Memories Table

```text
memories
--------
id
user_id
memory_type
memory_value
created_at
```

Conversation history is retrieved using `user_id` and `session_id`.

Long-term memories are retrieved using `user_id`.

The memory table supports multiple distinct values within a memory category.

The database uses a uniqueness constraint to avoid storing the same memory type and value repeatedly for a user.

## 13. Design Decisions

### Why FastAPI?

FastAPI provides a lightweight Python framework with request validation and automatic Swagger documentation.

### Why SQLite?

SQLite provides persistent storage without requiring an external database server.

It is suitable for a local machine-coding assignment.

### Why Rule-Based Memory Extraction?

Regular expressions offer a simple, deterministic way to extract supported memory categories without making additional LLM calls.

### Why Keyword-Based Retrieval?

Keyword matching is lightweight, inexpensive, and sufficient for the assignment's small collection of structured user memories.

### Why Not LangGraph?

The application follows a straightforward sequence of operations.

There is no requirement for multiple agents or complex orchestration.

### Why Not a Vector Database?

The assignment does not require semantic search.

For the implemented memory categories and tested queries, category filtering and keyword scoring provide a simple baseline.

## 14. Known Limitations

- Regex-based extraction supports limited phrasing patterns.
- Keyword-based retrieval does not provide semantic understanding.
- Complex memory corrections and conflicts are not fully handled.
- There is no dedicated token-budget limit for long-term memories.
- Authentication and authorization are not implemented.
- SQLite is intended for local development rather than distributed high-concurrency workloads.
- The application requires Azure OpenAI connectivity for response generation.
- Memory extraction and saving occur before the LLM call, while conversation messages are saved after successful generation.
- Automated functional tests are included, but there is no dedicated evaluation pipeline for semantic retrieval or personalization quality.

## 15. Potential Improvements

For a production implementation, possible enhancements include:

- PostgreSQL for concurrent database access.
- Authenticated user identity.
- Semantic or hybrid memory retrieval.
- Memory confidence, freshness, and conflict resolution.
- Context token-budget management.
- LLM observability and evaluation.
- Improved failure handling and provider fallback.
- User-facing memory review and deletion controls.

These enhancements are outside the current assignment scope.

## 16. Conclusion

This project demonstrates a personalized AI chat backend with session-based conversation history, persistent user memories, relevance-based memory retrieval, and Azure OpenAI response generation.

The implementation prioritizes simplicity, modularity, testability, and the core requirements of the MyNaksh machine-coding assignment.
